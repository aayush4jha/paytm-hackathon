# 场景设计法：测产品 + 抓包合一

调研的支柱 2（实际使用）最有效的做法，是设计一组测试场景，**让每个场景同时干两件事**：看产品的输出形态（产品维度），和抓一份干净的网络样本（技术维度）。一份操作，两份收获。

## 设计原则

1. **每个场景独立新建会话** —— 避免上下文污染，拿到干净的抓包样本。
2. **每个核心功能对应一个场景** —— 覆盖不同的输出形态（纯文本 / 生成文档 / 解题 / 图 / 视频…）。
3. **prompt 中英文混合** —— 顺便检验产品的 i18n 处理（语言感知检索、双语策略等）。
4. **聚焦差异化产出** —— 优先设计能触发"它和别人不一样的地方"的场景（图、节点框、引文、视频）。

## 每个场景要记的字段

| 字段 | 说明 |
|------|------|
| Prompt | 原文（中英混合那条照抄） |
| 期望产出 | 跑之前的预判 |
| 重点观察 | 这个场景专门要看什么（公式渲染？文件上传链路？视频生成？） |
| 抓包关注 | 这个场景预期能抓到什么请求 |

## 公共测量项（每个场景都记）

- 提交时间 T0
- 首字时间（流开始）
- 完成时间
- 总请求数 / API 调用数
- 有没有触发副作用（写知识库？更新用户画像？）

## agent 产品：探测自适应行为

agent 类产品（多步编排）不是每条 query 都跑同一套。别只跑一条——测三类对比：

- **简单直答**（"一句话解释 X"）：看它跳过哪些步骤（常跳反向问询）。
- **复杂结构化**（"分步讲解 X 并配图"）：触发完整流水线。
- **会话内追问**（在已有会话里追问"再举个例子"）：看后续轮次有多轻。

对比每类各调了哪些 tool，就能摸清"首轮重、后续轻"这类自适应路由和每轮成本——这是 agent 产品很关键的一笔，单跑一条看不出来。顺手扫服务端在 payload 里漏的元数据（model / provider / version / *_id），常能破"以为拿不到"的项（方法见 `references/network-capture.md`）。

## 执行顺序：由简到繁

先用**最简单的纯文本场景**把抓包通路打通，再逐步上复杂的（解题 → 生成文档 → 图/视频 → 文件上传）。最重型的（视频、大文件）放在抓包链路成熟之后。这样不会一上来就被复杂场景的噪声淹没。

## 取舍：要不要把每个场景都跑完？

不一定。如果某一个场景（尤其是最复杂、覆盖机制最全的那个）一次就把核心协议、schema、tool 栈全暴露了，后面几个场景的边际信息可能很低，可以跳过或只做 UI 流程探索，在文档里注明"S2/S3 跳过，原因：S5 已覆盖核心机制"。诚实标注比硬跑一遍更有价值。
