# 产品调研 (Product Research)

把"调研一个线上产品"从一次性的零散探索，变成可复用、可审计、产出高可读性文档的标准流程。

## 何时用

用户想搞清一个线上产品：它是什么、给谁用、怎么实现的、怎么赚钱、和主流产品比差在哪。典型触发：调研竞品、扒一个 AI 产品的实现、teardown 一个 web app。

这个 skill 的价值不在于"挖到机密"，而在于**把拿得到的信息系统化、把推断和事实分清楚、把结论写成别人能快速读懂的文档**。

## 访问层级：动手前先定盘

调研能挖多深，取决于你能拿到多少代码。先判断自己在哪一层——它决定你的主要手段，也决定外部抓包是唯一信息源还是只是验证手段。

| 层级 | 你手上有什么 | 主要手段 | 外部抓包的角色 |
|------|-------------|---------|---------------|
| 白盒 | 完整仓库（开源 / 自家产品 / 获授权） | 直接读代码 | 仅做行为验证 |
| 灰盒 | 前端代码可还原（source map / 未混淆 bundle） | 读前端源码 + 抓包补后端 | 补全代码看不到的后端行为 |
| 黑盒 | 只有线上产品 | 外部观察 + 抓包 | 唯一手段 |

原则：**能读代码就别靠猜**。层级越高，文档里的"推测"越少、provenance 越硬；有代码时，外部观察从"主要信息源"降级为"验证手段"。怎么判断访问层级、怎么还原前端代码、拿到仓库后先读哪里，见 `references/code-access.md`。

边界随层级移动：黑盒下服务端的模型选型 / prompt / 数据库逻辑确实拿不到（进 `open-questions.md`）；但只要有对应层级的代码访问，这些就不再是盲区。**只研究你有权访问的代码**——开源项目、你自己的产品、产品公开 ship 的 source map、或明确获授权的仓库；不要为调研去搞未授权的私有代码。

## 登录优先：被 auth 挡住时先引导用户

登录态产品一旦被登录页挡住，**不要马上退回纯公开资料调研**。先用一句话告诉用户登录后能多拿到什么（真实使用流程、实时帧、权限/计费/设置页、模型或 runtime 元数据），以及你会遵守哪些边界（不替用户输密码、不改设置、不发布、不消费重额度）。然后把浏览器交给用户本人登录。

如果用户暂时不登录、登录失败，或产品需要额外授权，就继续做公开信息 / 前端 bundle / 公开包 / CLI 的替代调研，但必须在 `open-questions.md` 单独登记：
- 没拿到什么；
- 为什么这次拿不到；
- 登录后怎么补；
- 本次结论因此降到什么确定性。

原则：**先争取登录态，拿不到再 fallback；fallback 不是结束，而是带着清晰边界继续推进**。

## 产出结构

固定目录，每个文件有唯一职责（见 `templates/`）：

```
<product-name>/
├── 00-overview.md          # 总览 + 关键数字表 + 术语表（全局唯一信息源）
├── 01-product-definition.md# 定位 / 团队 / 定价 / 商业模式
├── 02-usage-flows.md       # 实际使用：场景设计 + 输出形态观察
├── 03-network.md           # 端点 / 协议 / 鉴权 / 流式抓包
├── 04-frontend.md          # 前端技术指纹
├── 05-differentiation.md   # 与主流产品横向对比 + 差异化分析
├── 99-synthesis.md         # 综合复盘（只做导读 + 链接，不复述正文）
├── open-questions.md       # 所有"没拿到 / 待验证"集中地
└── raw/                    # 原始抓包归档（json / txt / 截图），不进正文
```

复制 `templates/` 下同名文件起步。每个模板里有内联指引（HTML 注释）和正反例，照着填。

## Provenance 纪律：每条事实都要能追溯

调研最大的风险是**把推断当事实写**。规则：

- 每个发现都标注**来源 + 工具**（哪个页面/抓包，用什么工具拿到的）。
- 明确区分三种确定性，写的时候要让读者一眼看出来：
  - **观察到的**：直接看到的（DOM 文本、抓到的帧、JS 探针返回值）→ 平述。
  - **推断的**：基于证据的合理推测 → 用"推测 / 大概率 / 暗示"标明，并给出推断依据。
  - **没拿到的**：服务端不可见或本次没触发 → 进 `open-questions.md`，不在正文假装知道。但**写进 open-questions 前先确认它真的拿不到**：后端用的模型、检索 API、内部版本这类"以为是服务端机密"的东西，常明文漏在发给客户端的 payload 里（如 `model_used` 字段）。先翻一遍客户端流量，方法见 `references/network-capture.md`。

绝不要因为"读起来更顺"就把"推测 X 用了 Gemini"写成"X 用了 Gemini"。诚实的边界本身就是高质量调研的标志。

## 可读性硬规则（这套文档好不好读，靠这几条强制保证）

调研文档最常见的崩坏是：同一件事在五个文件里重复、数字各处对不上、满屏加粗导致没有重点。下面每条都是**可检查**的约束，不是口号。填模板和写正文时必须遵守，交付前用「自检闸」逐条过。

### 1. 唯一信息源 —— 防重复

每类事实只在它的 home 文件里**详述一次**。别的文件要用到，只贴链接，不复制段落。
- 网络层事实 → 只在 `03-network.md`；产品定价 → 只在 `01-product-definition.md`；以此类推。
- `99-synthesis.md` 是重灾区：它只能写"一句话结论 + 链接到详述处"，**禁止把支柱正文搬过来**。模板结构上就没给复述的位置。

### 2. 数字单一定义 —— 防漂移

所有关键数字（端点数、事件类型数、节点种类数、延迟、价格…）**只在 `00-overview.md` 的「关键数字」表里定义一次**。正文要提某个数字，必须和那张表一致。
- 交付前做一遍数字核对：把正文里出现的数字跟「关键数字」表对一遍，对不上就改。
- 反面教材：标题写"6 种节点框"正文却列 8 种；一处说"7 个 tool"另一处说"8 个"。这种不一致直接摧毁读者信任。

### 3. 强调预算 —— 防强调通胀

强调用多了等于没强调。
- **每节最多 1 处加粗**。真正的核心结论才配加粗。
- ✅ / ❌ **只允许出现在纯对比表里**表示"有/无"，不许拿来当强调符号撒在正文。
- 禁用 `★`、"重大发现"、"重磅"、"你最关心的"这类自我标榜的词。让事实本身有分量。

### 4. 表格门槛 —— 防表格泛滥

表格只配用在**真正的对比或映射**上（≥3 列，或多行同结构条目）。
- 2 列的"维度 | 值"表本质是列表，改成短句或 `-` 列表。
- 讲因果、讲取舍、讲"为什么这么选"——用**散文**。这些是有逻辑链的内容，塞进表格会被切碎。

### 5. 术语词表 —— 防术语劝退

`00-overview.md` 必须有「术语表」小节。任何缩写（ReAct / CSR / SSE / RAG / BaaS / JWT / TTFC …）**首次出现时**要么就地一句话解释，要么已在术语表里有定义。产品报告面向的读者可能不懂技术黑话。

### 6. 不确定性集中 —— 防 TODO 散落

所有"没拿到 / 待验证 / 待确认"集中进 `open-questions.md` 一个文件。其他文件需要提及时只链接过去。这样读者能一眼看到整套调研的不确定面有多大，而不是散落在十个文件末尾各写一段。登录态被挡住、用户暂不登录、公开包和真实线上行为不一致这类边界，也都进这里，不要只在 final 里口头说明。

## 交付前自检闸

**声明调研完成前，逐条过这张清单。任何一条不过，回去改。**

- [ ] **唯一信息源**：没有任何一个事实在两个文件里被详述两遍？（重复的已改成链接）
- [ ] **synthesis 干净**：`99-synthesis.md` 只有结论 + 链接，没有搬运正文？
- [ ] **数字一致**：正文每个数字都能在「关键数字」表里找到，且对得上？
- [ ] **标题对账**：每个"N 种 / N 个"标题的数字 = 正文实际列出的条数？
- [ ] **强调克制**：每节加粗 ≤ 1 处？没有 ★ / "重大发现" 这类词？✅❌ 只在对比表里？
- [ ] **无废表**：没有 2 列"维度|值"表？（已改列表或散文）
- [ ] **术语可查**：每个缩写首次出现都有解释或在术语表里？
- [ ] **不确定性集中**：所有"没拿到/待验证"都在 `open-questions.md`？
- [ ] **provenance 完整**：每个非显然的事实都能追溯到来源+工具？推断都标了"推测"？
- [ ] **脱敏到位 + 已复验**：没有真实 PII 写进文件，且脱敏后 grep 复验过残留？（见下）

## PII 脱敏

调研登录态产品时，JWT / DOM / 抓包里会带出账号信息（email、姓名、avatar URL、用户 UUID）。
- 这些**一律不写进任何文件**，用 `<REDACTED>` 占位。
- 临时变量（如浏览器里 dump 出来的对象）里的 PII 同样处理。
- 结构信息可以留（"JWT 含 email 字段"），具体值不留。
- **脱敏后必须复验**：grep 一遍残留再收工。PII（尤其用户画像 / memory）常被模型复述到 thinking / guideline / 正文多处，只匹配 memory 那一处会漏过别处——血泪教训。
- **区分用户 PII 与公开数据**：别把合法引用、公开 URL（如搜索结果里的域名）当 PII 误删；只涂能指向具体某个人的东西。
- **抓包钩子默认只存字段名、不存值**（防夹带 PII）；确需某个安全字段的值（如 `model_used`）时，定向只取那一个字段。

## 登录态调研规范

调研登录态产品（agent 工作台、SaaS）绕不开用用户账号。守这几条：

- **优先引导用户本人登录**：如果产品核心信息在登录后，先说明登录价值和操作边界，请用户本人完成登录；不要因为未登录页面可访问就默认只做浅层调研。
- **用账号做任何动作前，先说清楚**：会输入 / 提交什么、消耗什么额度、不碰哪些东西（历史 / 设置 / 订阅，不发布不分享）。说明之后再动手，输入用中性内容。
- **不替用户登录**：输密码、走 Google / OAuth 授权由用户本人完成。会话 token（JWT 常 ~2h）中途过期掉登录是常态 → 调起浏览器交还用户重登，登好再继续，别自己代登。
- **反爬**：登录态 / 有 Cloudflare 挑战页的产品，curl / WebFetch 直接吃 403，必须用能过挑战的真实浏览器。详见 `references/tool-playbook.md`。

## 资料留存（支柱 6）

边调研边把**原始证据**存进 `raw/`，别等最后补：
- 流式抓包 → `raw/<scenario>-frames.json`
- 整页文本 → `raw/<scenario>-fulltext.txt`
- 关键截图 → `raw/<scenario>-<step>.png`

正文引用结论时指向 raw 里的原始档。原始档不进正文，避免正文被噪声淹没。

网络层 teardown 的两份标准产出（建议都留）：
- **解析版 wire-trace 范本**：一个 query case 的完整事件时间线 + 每种事件类型一个完整 JSON 样本（脱敏）。让人看懂"协议长什么样"。
- **完整 raw 帧 dump**：某次会话的逐帧原始流（`.jsonl`，仅脱敏 PII + token，其余字节原样）。取数技巧见 `references/network-capture.md`。

**可视化更易懂时就做 demo**：当某段流程 / 协议靠文字难讲清（agent 的多步编排、流式 + 异步回填的联动），用捕获的真实数据做一个**交互式重放**（单文件 HTML、时间轴重放真实帧、协议 → 编排 → UI 三联动）能大幅提升理解。收益明显时优先做，别硬性要求。
