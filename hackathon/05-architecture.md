# Haq — Architecture

Design principle: **the LLM reads and writes, the rules engine decides the numbers, tools take the actions, and humans own judgement.** No amount of money shown to a customer or sent to an insurer is ever generated by the LLM. Every amount comes from the deterministic entitlement engine, with a trace back to the clause and circular behind it.

## 1. System overview

```
 CHANNELS            Paytm app (chat + cards) · WhatsApp · Voice (AI Soundbox / IVR, 11 languages)
                                   │
                           API Gateway + Auth (Paytm SSO, OTP step-up for sends)
                                   │
 ┌─────────────────────────────── CASE ORCHESTRATOR ─────────────────────────────────┐
 │  Stateful agent loop per hospitalisation "case" (state machine + LLM planner)     │
 │  States: INTAKE → COVER → ADMIT → STAY → DISCHARGE → SETTLED → CONTEST → ESCALATE │
 │                                    → CLOSED                                       │
 └───┬──────────┬───────────┬────────────┬────────────┬────────────┬─────────────┬───┘
     │          │           │            │            │            │             │
  Consent    Policy     Document     Entitlement   Clock       Advocate     Communicator
  & Intake   Intel.     Intel.       Engine        Keeper      (Action)     (plain-language,
  agent      agent      agent        (NO LLM)      (timers)    agent        vernacular, voice)
     │          │           │            │            │            │             │
     └──────────┴───────────┴──── Verifier / Guardrail layer ─────┴─────────────┘
                                   │
               Human Claims-Expert Console (handoff with full case file)

        Versioned rulebook (YAML, per circular) · Encrypted document vault · Consent artefacts
 TOOLS: Paytm Policy API · NHCX-shaped FHIR claim API · Hospital tariff · DigiLocker/ABHA
        Email/insurer portal · Bima Bharosa form · Scheduler · Notification (push/WhatsApp/SMS)
```

## 2. Agents and responsibilities

| Agent | Responsibility | Model | Key tools | Output |
|---|---|---|---|---|
| **Case Orchestrator** | Plans the next step from case state and events; routes work to specialists; decides when to ask the user, act or escalate | Claude Sonnet 5 (planning) | All specialist agents; state store | Next action + reason, written to the audit log |
| **Consent & Intake** | Verifies identity; captures a DPDP-compliant consent artefact (purpose: "this claim"); fetches the policy | Claude Haiku 4.5 | Paytm Policy API, DigiLocker/ABHA (consented) | Case created, consent ID |
| **Policy Intelligence** | Parses the policy wording into a **Coverage Graph**: SI, room/ICU caps, co-pay, sub-limits, waiting periods, moratorium date, exclusions. Each node carries a clause ID | Sonnet (extraction) + clause index | PDF parser, clause index | `coverage.json` with clause refs |
| **Document Intelligence** | OCRs bills, settlement letters, discharge summaries and query letters; normalises each line into a **bill-line ontology** (room, nursing, surgeon, OT, pharmacy, consumable, implant, diagnostic, ICU, non-payable) | Claude vision + Haiku classifier | OCR, IRDAI non-payable list, ontology | Structured line items with a confidence score each |
| **Entitlement Engine** | Recomputes what should have been paid, rule by rule, with an explanation trace | **Deterministic code, no LLM** | Versioned rulebook | Entitled ₹, recoverable ₹, verdict per line |
| **Clock Keeper** | Starts and stops regulatory timers from events; detects breaches | Code | Scheduler, FHIR status | Timers, breach events |
| **Advocate (Action)** | Chooses the forum, drafts the contest or grievance, attaches evidence, and **sends only after user approval**; schedules the next rung of the ladder | Sonnet (drafting) | Email/portal, NHCX `Communication`, Bima Bharosa form, scheduler | Filed request + reference ID |
| **Communicator** | Turns every state change into plain-language, vernacular text or voice; answers "why?" by quoting the clause | Sonnet / Haiku | Translation, TTS/STT | User messages |
| **Verifier / Guardrail** | Checks every outgoing message: numbers match the engine; each claim has a citation; no guarantees; AI disclosure present; PII redacted | Haiku + rule checks | Engine output, citation index | Pass / block / escalate |

## 4. Data flow (settlement audit, the hero path)

```
Settlement letter + bill (photo) ──► Document Intel ──► line items {name, ₹, category, conf}
Policy wording ─────────────────► Policy Intel ────► Coverage Graph {room_cap: 5000 [§D.1(i)], ...}
                                                             │
         line items + coverage + rulebook ──► Entitlement Engine (deterministic)
                                                             │
          per-line verdicts: VALID / QUESTIONABLE / VIOLATION + rule trace + recoverable ₹
                                                             │
                   Verifier (numbers == engine? citations present?) ──► Communicator ──► user
                                                             │
                     user taps "Contest" ──► Advocate drafts ──► user approves (OTP) ──► send
                                                             │
                     Clock Keeper: 14-day grievance timer ──► auto-draft Bima Bharosa ──► Ombudsman
```

## 5. Memory and context

- **Case memory (per hospitalisation):** the state, all documents, the Coverage Graph, the engine results, every message and action, and the clocks. The customer never repeats themselves, and a human expert opens the same case file.
- **User memory (long-lived, consented):** policies, family members covered, preferred language, and past cases (for renewal advice). Kept under DPDP purpose limitation and deletable on request.
- **Knowledge (shared, versioned):** a clause index for each policy wording (UIN-keyed) and the **rulebook**: IRDAI Health Master Circular 2024, the June 2020 proportionate-deduction guidelines, the IRDAI non-payable items list and the grievance timelines. Each rule is stored as code plus source text plus an effective date.

## 6. RAG: where it is used and where it is not

- **Used:** finding the clause that answers "is X covered?", citing the exact wording back, and retrieving the relevant circular paragraph for letters.
- **Not used for decisions:** coverage limits are extracted once into the Coverage Graph and checked by the Verifier against the source text. Amounts come from the engine. Retrieval only ever **supports** a statement with a quote. It never produces the number.

## 7. Decision logic (entitlement engine rules used in the demo)

| Rule ID | Source | Logic |
|---|---|---|
| R1 Room cap | Policy §D.1(i) | payable_room/day = min(actual, cap) |
| R2 Proportionate deduction | Policy clause + **IRDAI/HLT/REG/CIR/151/06/2020** | If actual room > cap: factor = cap ÷ actual, applied **only to "associated medical expenses"** (nursing, surgeon/consultant fees, OT, doctor visits). **Never** applied to pharmacy, consumables, implants, diagnostics or ICU. Not applied if the hospital does not bill differentially by room. |
| R3 Non-payables | IRDAI list of non-payable items | Admin/registration fees, gloves, masks, toiletries: deduction VALID |
| R4 Co-pay | Policy §G.4 | Applied after all other rules |
| R5 Moratorium | Master Circular 2024 / Policy §F.13 | After 60 continuous months, a non-disclosure contest is invalid except for proven fraud |
| R6 Clocks | Master Circular 2024 | Pre-auth ≤1 h; discharge ≤3 h (the insurer bears extra charges); settle ≤15 days per wording, else interest at bank rate + 2%; grievance 14 days, then Bima Bharosa / Ombudsman |

Verdicts: **VIOLATION** means a rule was provably broken and the amount is exact. **QUESTIONABLE** means the mapping confidence is below 0.8, or the case depends on medical judgement. **VALID** means the deduction is explained to the user in plain words, so they understand why they are not getting it back.

## 8. Human escalation (explicit triggers)

1. The dispute is about **medical necessity** or treatment choice.
2. The insurer alleges **non-disclosure or fraud**.
3. The disputed amount is **over ₹1,00,000**, or it is a rejection of the whole claim.
4. Low confidence: OCR or mapping confidence below the threshold after one clarification attempt.
5. The Verifier finds a mismatch between the LLM text and the engine numbers.
6. The user asks for a human, or shows distress. There is a one-tap button on every screen.
7. Two ladder rungs are exhausted without resolution.

The handoff sends a case summary, all documents, the engine trace, the drafts and the clock status. SLA: first human response within 5 minutes during service hours.

## 9. Guardrails

- **Disclosure:** "You're talking to Haq, an AI assistant. A human expert is one tap away." This follows RBI FREE-AI and good broker practice.
- **Grounding:** every coverage statement quotes a clause. Every rule statement names the circular. This is the lesson of *Moffatt v. Air Canada*, where the company was held to what its chatbot promised.
- **No guarantees:** the wording is "you are likely entitled to", never "you will get".
- **Consent to act:** nothing is sent without an explicit per-action approval with OTP step-up. Drafts stay editable.
- **Role integrity:** Haq never recommends hiding facts on a proposal form and never alters documents.
- **Anti-flooding:** contests are filed only for VIOLATION lines, or QUESTIONABLE lines after a human review.

## 10. Security and privacy (health data is sensitive personal data under DPDP)

- A consent artefact per purpose (claim assistance), time-bound and revocable. ABDM/AA-style consent where available.
- Name, Aadhaar, phone and policy number are redacted before LLM calls and re-inserted after. Only the minimum needed text is sent to the model.
- Data stored in India, encrypted at rest (KMS) and in transit. Documents live in a vault with signed URLs.
- Append-only audit log of every agent decision, tool call and approval. It is exportable for the insurer, IRDAI or the customer.
- Role-based access for the human experts console. Access is logged.

## 11. Failure handling

| Failure | Behaviour |
|---|---|
| Blurry bill / low OCR confidence | Ask the user to confirm the specific fields ("Is this ₹38,000?") or retake the photo. Never guess an amount. |
| Policy wording not found | Ask for the PDF or fetch it from DigiLocker. Until then give generic guidance, clearly labelled. |
| Insurer/NHCX API down | Queue and retry with backoff. Tell the user. Clocks keep running from the last known event. |
| Insurer silent past the deadline | Record the breach and move to the next ladder rung automatically (a draft for approval). |
| LLM output fails the Verifier | Block it, regenerate once, then escalate to a human. |
| User abandons mid-flow | Case memory persists. A gentle reminder comes before any deadline the user might miss. |

## 12. Hackathon tech stack

- **Frontend:** Next.js mobile web mimicking the Paytm app (claim card, timeline, deduction audit view, approval sheet), plus a small human-expert console.
- **Backend:** FastAPI (Python). The orchestrator uses the Claude Agent SDK / tool use with typed tools.
- **Models:** `claude-sonnet-5` for planning and drafting, `claude-haiku-4-5` for classification and the Verifier, Claude vision for bill OCR.
- **Storage:** Postgres + pgvector (cases, clause index, audit log). Local file vault.
- **Mocks:** a FastAPI mock NHCX FHIR server; mock tariff and policy APIs; a sandbox email inbox.
- **Observability:** a structured event log rendered as the "agent trace" panel in the demo, so judges can watch each reasoning step and tool call.

## 13. Metrics and KPIs

Customer:
- ₹ recovered per case.
- % of out-of-pocket known before admission.
- Discharge wait from "advised" to "left".
- Contests filed within 10 minutes.

Quality:
- Contest precision (share upheld).
- Verifier block rate.
- Handoff rate and handoff response time.

Business:
- Paytm health policy renewal rate (Haq users vs others).
- Support contacts per claim.
- Ombudsman complaints per 1,000 claims (insurer view).
- Cost per resolved case.

## 14. Business impact and scale

- **For Paytm as broker:** claims are the moment of truth for renewal. A broker that recovers money for its customers gains a retention and trust advantage in a market where customers compare mainly on price.
- **For insurers, via Paytm Intelligence (B2B):** the same engine, run before settlement, catches deductions that break the rules before they become grievances. That cuts Bima Bharosa and Ombudsman volume (Star Health alone had ~12,000 Ombudsman complaints in FY25). It serves the customer and the insurer's compliance at the same time.
- **Scale by reuse:** the engine is generic (documents + rulebook + clocks + ladder). New verticals need only a new rulebook and tools:
  - credit-report dispute: 30-day clock, ₹100/day, RBI CMS
  - failed UPI payment: T+1, ₹100/day
  - motor claim: 24 h surveyor / 15-day report / 7-day decision
